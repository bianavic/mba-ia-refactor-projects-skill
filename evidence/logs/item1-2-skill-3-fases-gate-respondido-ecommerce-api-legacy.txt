## Summary
CRITICAL: 1 | HIGH: 5 | MEDIUM: 5 | LOW: 5

## Findings

### [CRITICAL] Hardcoded fallback password provisions real accounts with a known credential
File: src/models/userModel.js:4,16 (root cause: src/controllers/checkoutController.js:10-14)
Description: `userModel.create()` hashes `FALLBACK_PASSWORD = '123456'` whenever `rawPassword`
is falsy, and `checkout()` validates only name/email/courseId/cardNumber (line 12) — `pwd` is
never required — so any checkout that omits `pwd` silently creates a real account secured by a
password hardcoded in source.
Impact: every such account is protected by a credential anyone reading the repo already knows;
a direct account-takeover vector the moment any authentication endpoint exists.
Recommendation: AP-02 / RP-02 — require `rawPassword` and reject with 400 when missing.
Status: Still open (third consecutive round, code unchanged).

### [HIGH] Checkout performs a multi-step money-moving write with no transaction or compensation
File: src/controllers/checkoutController.js:42-56 (charge :42, enrollment :47, payment :53)
Description: The card is charged first, then the enrollment is inserted, then the payment row —
three sequential writes, no transaction, no rollback or compensating action on any of the three
failure branches, each of which just returns 500.
Impact: a failure at :47 leaves the customer charged with no enrollment and no payment record —
money taken, nothing delivered, nothing to reconcile against. A failure at :53 leaves an
enrollment the report never attributes revenue to, since it sums only `PAID` rows
(reportController.js:36). Both states are silent and need manual DB surgery.
Recommendation: AP-05 / RP-01 — move the sequence into a `checkoutService` owning one
transaction boundary; charge only once persistence is known to succeed, or record a reversal.
Status: New.

### [HIGH] Business orchestration and aggregation live in controllers instead of a service layer
File: src/controllers/checkoutController.js:9-62; src/controllers/reportController.js:28-43
Description: `checkout()` orchestrates five models plus the gateway, audit log and cache — the
entire domain workflow, not HTTP concerns. `financialReport()` computes the aggregation in the
handler: grouping rows by course (:28-32) and deriving revenue from `PAID` rows only (:36).
`services/` holds only the fake gateway and the cache — no domain service.
Impact: neither the checkout workflow nor the revenue rule is unit-testable without Express
req/res and a live SQLite handle; "revenue counts only PAID payments" is invisible to the model
layer and will be re-implemented differently by the next report or invoice endpoint.
Recommendation: AP-05 / AP-06 / RP-01 — extract `checkoutService` and `reportService`;
controllers keep parse → one service call → serialize.
Status: New — a consequence of round 1's Phase 3, which created controllers and models but no
domain service layer.

### [HIGH] Duplicated, ad hoc error handling bypasses the centralized handler — one path unguarded
File: src/controllers/checkoutController.js:17-21,25-29,35-39,46-50,52-56,58;
      src/controllers/reportController.js:12-16,22-26; src/controllers/userController.js:6-10;
      src/middlewares/errorHandler.js:1-8
Description: Every model call carries its own try/catch mapping to a hand-written response, even
though app.js:14 already registers a centralized `errorHandler`. Line 58
(`await auditLogModel.create(...)`) has no guard at all — Express 4 does not forward a rejected
promise from an async handler, so a failure there reaches neither path and the request hangs.
Impact: nine near-identical blocks that have already drifted (text vs JSON, different messages
for the same failure class), plus an unhandled rejection that can hang a connection.
Recommendation: AP-06 / RP-11 — async-error adapter + `next(err)`; delete the boilerplate.
Status: Still open (unchanged since part2).

### [HIGH] Cascade delete swallows errors and reports success for users that do not exist
File: src/models/userModel.js:26-40 (unguarded `db.run` at :29-32 and :33);
      src/controllers/userController.js:3-13
Description: Of the three statements in `db.serialize`, only `DELETE FROM users` passes an error
callback — the payments (:29-32) and enrollments (:33) deletes drop their errors and the promise
still resolves. `this.changes` is never inspected, so deleting a non-existent id resolves and
the controller replies 200 with "Usuário e seus registros associados ... foram deletados."
Impact: a partial cascade failure is indistinguishable from success — the caller is told
enrollments and payments were removed while they are still there, which is exactly the
orphaned-records corruption round 1 was supposed to close. `DELETE /api/users/9999` likewise
reports a deletion that never happened.
Recommendation: AP-06 / RP-11 — error callback on every statement (or promisified `db.run`
awaited inside a transaction), check `this.changes`, return 404 on no match.
Status: New — both previous reports treated the orphaned-records finding as resolved on the
strength of the statements being present, without checking their error handling.

### [HIGH] Global mutable, unbounded, write-only cache
File: src/services/cacheService.js:1-15; written at src/controllers/checkoutController.js:59
Description: A module-level singleton `Map` mutated from every checkout with no eviction, TTL or
size bound. Project-wide grep confirms `cacheService.get` is called from nowhere.
Impact: memory grows without bound (one `last_checkout_<userId>` key per user who ever checks
out), mutated from concurrent handlers with no synchronization, for zero functional benefit.
Recommendation: AP-07 / RP-05 — wire it into a read path or delete it; if kept, bound it.
Status: Still open (unchanged since part2).

### [MEDIUM] No request validation layer — route parameters are never validated
File: src/routes/index.js:8-10; src/controllers/checkoutController.js:10-14;
      src/controllers/userController.js:4
Description: The three routes register handlers with no validation middleware. `checkout` does a
bare truthiness check on four fields (:12) — `c_id` goes to the query unchecked, `card` goes to
`maskCard()` with no type or length check. `deleteUser` hands `req.params.id` straight to the
model.
Impact: a non-string `card` (e.g. `{"card": 123}`) reaches `cardNumber.slice()` in
paymentGatewayService.js:7 and throws a TypeError inside an unguarded async handler; a
non-numeric `c_id` matches nothing and returns 404 instead of 400, so clients cannot tell a
malformed request from a missing course.
Recommendation: AP-09 / RP-07 — validation middleware or per-route schema at the boundary.
Status: New.

### [MEDIUM] Dead configuration fields (DB/SMTP credentials never consumed)
File: src/config/index.js:4-5,7 (`dbUser`, `dbPass`, `smtpUser`); .env.example:1-2,4
Description: All three are read into the exported config object and referenced nowhere else in
`src/`. The app uses in-memory SQLite (no credentials) and never sends email.
Impact: misleads readers into believing external DB auth and SMTP are wired up; if ever given
real values they become live credentials with no consumer.
Recommendation: AP-10 / RP-10 — delete them and their `.env` entries, or wire them up.
Status: Still open (unchanged since part2).

### [MEDIUM] Pagination present but unbounded
File: src/controllers/reportController.js:7-9
Description: `per_page` is floored at 1 via `Math.max(...)` but never capped — `per_page=999999999`
returns every course plus every joined enrollment/payment row.
Impact: defeats the pagination already implemented; one request still forces the full-table scan
and payload the mechanism exists to prevent.
Recommendation: AP-09 / RP-07 — add `Math.min(perPage, 100)` alongside the floor.
Status: Still open (unchanged since part2).

### [MEDIUM] Password verification is implemented but unreachable — and broken if it were reached
File: src/utils/crypto.js:11-17
Description: `verifyPassword()` is exported but called from nowhere; there is no login route at
all, so `hashPassword` writes credentials nothing ever reads. It is also latently broken:
`crypto.timingSafeEqual` throws `RangeError` when its buffers differ in length, so a stored hash
of unexpected length raises instead of returning `false`.
Impact: a reader of `utils/crypto.js` reasonably concludes authentication exists; it does not.
The bug surfaces only the day someone wires it up.
Recommendation: AP-10 / RP-10 — add the auth route it implies or remove it; if kept, compare
lengths before `timingSafeEqual`.
Status: New.

### [MEDIUM] The app binds the port at import time, so it cannot be loaded without starting a server
File: src/app.js:8-20 (`initSchema()` :11, `app.listen(...)` :16, `module.exports = app` :20)
Description: App construction, schema bootstrap and `listen` all run as module side effects, then
the app is exported. `listen` has already fired by the time the export is visible.
Impact: the export exists for tests but is unusable by them — importing binds port 3000 and fails
with `EADDRINUSE` when a server is running (a real constraint: CLAUDE.md notes projects 1 and 3
already contend for one port). The schema bootstrap is also uncontrollable from a test.
Recommendation: AP-05 / RP-01 — split `app.js` (configured app, no side effects) from
`server.js` (`initSchema()` + `listen`); point `main`/`start` at the latter.
Status: New.

### [LOW] Inconsistent language/naming conventions
File: src/controllers/checkoutController.js:10,13,20,22,28,38,49,55;
      src/controllers/reportController.js:15,25; src/controllers/userController.js:9,12
Description: Portuguese user-facing strings mixed with English identifiers, and abbreviated
request fields (`usr`, `eml`, `pwd`, `c_id`, `card`) destructured into descriptive internal names.
Impact: slows onboarding; :10 is the only place the two vocabularies are reconciled.
Recommendation: AP-15 / RP-15 — one convention for new/internal code; per RP-15's scope limit the
existing field names and message strings are API contract and should be documented, not renamed.
Status: Still open (expected to stay documented rather than fixed).

### [LOW] Inconsistent response-format conventions
File: src/controllers/checkoutController.js:13,20,22,28,38,49,55,61;
      src/controllers/userController.js:9,12; src/controllers/reportController.js:18,45
Description: Plain-text bodies mixed with JSON bodies across the same route layer, and the one
JSON success payload mixes snake_case (`enrollment_id`) with the camelCase used everywhere else.
Impact: clients cannot rely on one content type or casing and must special-case per endpoint.
Recommendation: AP-15 / RP-15 — standardize on JSON; `enrollment_id` is contract, document it.
Status: Still open (unchanged since part2).

### [LOW] Pagination default hardcoded outside the config module
File: src/controllers/reportController.js:4
Description: `DEFAULT_PAGE_SIZE = 20` sits in the controller instead of `config/index.js`, which
already centralizes `port` and `logLevel`.
Impact: changing it means editing a controller, and it cannot be overridden per environment.
Recommendation: AP-13 / RP-13 — move it into `config/index.js` as env-overridable.
Status: Still open (unchanged since part2).

### [LOW] Unknown routes bypass the JSON error contract
File: src/app.js:13-14; src/routes/index.js:8-10
Description: `app.use(routes)` is followed directly by `app.use(errorHandler)` with no catch-all
404 in between, so an unregistered path falls through to Express's built-in final handler and
returns HTML (`<pre>Cannot GET /api/nope</pre>`), never reaching `errorHandler`.
Impact: the API answers unknown paths with HTML while every handled error answers JSON — a client
parsing JSON breaks on exactly the case (typo'd or removed endpoint) where a clear error matters.
Recommendation: AP-06 / RP-11 — catch-all 404 middleware producing the same JSON shape.
Status: New.

### [LOW] Stale boilerplate metadata contradicts the project's actual identity
File: package.json:2-4; src/app.js:17
Description: The package is still named `desafio-arquitetura-ia-boilerplate` and described as
"Boilerplate com código legado para refatoração", the boot log still says "Frankenstein LMS" — a
name appearing nowhere else — and `scripts` has only `start`, no `test`, despite
`manual-tests.sh` and `arch-check.sh` sitting at the project root.
Impact: the manifest and the first line of every boot log describe a codebase that no longer
exists, and the two validation scripts are undiscoverable through `npm run`.
Recommendation: AP-13 / RP-13 — accurate `name`/`description`, service name from config, expose
the scripts via `npm test` / `npm run arch-check`.
Status: New.
